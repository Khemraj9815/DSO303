# Exam peak and loss of one Availability Zone

**Exam peak.** 3,000 students starting within 5 minutes is about 10 exam starts per second. Autosave adds 3,000 ÷ 30 s, about 100 writes per second. CloudFront serves the page from its edge cache. The API is a Lambda function, which scales per request. At ~100 req/s and ~150 ms each, about 15 run at once. Production would raise the account's concurrency quota above the default of 10 and add RDS Proxy to pool database connections. Each autosave is one small row update; the database instance class can be raised before exam week. The submission burst at the deadline goes onto SQS, so marking never slows the exam API; failed jobs retry, then land in a dead-letter queue. 50 MB uploads go straight to S3 with presigned URLs and never touch the API. WAF's per-IP rate limit is high (5,000 per 5 minutes) because a campus may share one IP.

**Loss of one AZ.** The ALB has nodes in both public subnets. The API Lambda has network interfaces in both private subnets and runs from the healthy one. Each AZ has its own NAT gateway, so neither depends on the other. RDS Multi-AZ replicates synchronously to a standby in the second AZ. If the primary's AZ fails, RDS promotes the standby and keeps the same endpoint, and no committed answer is lost. During the switch the page keeps answers in `localStorage` and retries, so at most about 30 seconds of typing is at risk. That is inside the 5-minute RPO; RDS also ships transaction logs every 5 minutes for point-in-time restore. S3, SQS, Lambda, Cognito and CloudFront are multi-AZ by design.

**Tested:** a forced RDS failover moved the primary from us-east-1b to us-east-1a. The API was unavailable for around 1-2 minutes.
